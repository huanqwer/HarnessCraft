## 1. 别让AI给你shit上雕花

这一章的标题可能有点粗俗

但这是我能在无数次踩坑后

总结出的最精准的表述

什么是"shit上雕花"

就是

**你的基础架构已经是烂的了

但你让AI在这个烂的基础上

雕出花来**

举个例子

你的项目结构混乱

没有清晰的模块划分

没有统一的代码规范

没有Spec约束

然后你让Agent在这个基础上"加一个新功能"

Agent会非常"努力"地

在这个混乱的代码库中

找到它认为合适的地方

插入新代码

然后给你一段"看起来能跑"的实现

你一看

功能确实实现了

代码确实能跑

但整个项目的混乱程度又增加了一层

这就是"shit上雕花"

### 1.1 为什么AI会"shit上雕花"

AI不会拒绝你的请求

这是它的天性

无论你的项目有多烂

它都会"尽力"完成任务

它不会说"你的架构太烂了，我建议先重构"

它只会说"好的，我来帮你加这个功能"

然后在你的烂架构上

再加一层"看起来能跑"的代码

这跟人类开发者不同

人类开发者遇到烂代码

会抱怨、会抗议、会建议重构

但AI不会

它永远"配合"

而这种"配合"

在长期来看

是对项目最大的伤害

### 1.2 如何避免"shit上雕花"

避免的方法很简单

但执行很难

**先修基础，再加功能**

具体来说

- 项目结构不清晰 → 先整理结构，再加功能
- 没有代码规范 → 先定义规范，再写代码
- 没有Spec约束 → 先写Spec，再让Agent执行
- 没有测试覆盖 → 先补测试，再改代码
- 没有CICD → 先搭流水线，再频繁部署

这些"基础工作"

看起来不产出"新功能"

但它们是所有后续功能的地基

地基不稳

上面建什么都会塌

### 1.3 定期"还技术债"

即使你做到了"先修基础"

随着项目推进

技术债也会不断积累

因为Agent生成的代码

虽然每次都"能跑"

但可能不完全符合最优实践

多次叠加后

就会出现

- 重复的代码片段
- 不一致的接口风格
- 过时的依赖版本
- 失效的测试用例

所以定期"还技术债"是必须的

我们团队的做法

每两周安排一次"技术债清理日"

这一天不开发新功能

专门让Agent做以下事情

- 识别和消除重复代码
- 统一不一致的接口风格
- 升级过时的依赖
- 修复失效的测试用例
- 优化性能瓶颈

**新功能让你走得快

但技术债清理让你走得远**

## 2. 熵管理

"熵"是一个物理学概念

简单来说

它衡量的是"混乱程度"

一个系统的熵

总是趋向于增加

这就是热力学第二定律

软件项目也不例外

随着代码量增加

功能不断叠加

人员来来去去

项目的"熵"会不断增加

表现为

代码越来越乱

依赖越来越多

逻辑越来越复杂

理解越来越困难

在Harness Coding中

这个问题更加严重

因为Agent生成代码的速度远快于人类

熵的增加速度也远快于传统开发

### 2.1 Harness Coding中的熵增来源

| 来源 | 具体表现 | 加速度 |
|------|----------|--------|
| 代码生成 | Agent快速生成大量代码 | 极快 |
| 风格漂移 | 不同Agent生成的代码风格不一致 | 快 |
| 依赖膨胀 | Agent引入新的依赖而不清理旧的 | 快 |
| Spec腐化 | Spec与实际实现逐渐脱节 | 中 |
| 测试失效 | 代码变更后测试未同步更新 | 中 |
| 文档过时 | 文档与代码不一致 | 慢但持续 |

### 2.2 熵管理的核心原则

熵管理的核心原则

**不是阻止熵增（不可能）

而是控制熵增的速度

并定期"减熵"**

具体策略

**策略一：约束先行**

在Agent生成代码之前

通过Rules、Skills、Design Token等约束

限定Agent的"自由度"

让它只能在"规定范围内"生成代码

这样即使熵增

也是在可控范围内的熵增

**策略二：定期重构**

每隔一段时间

对项目进行"减熵"操作

- 合并重复代码
- 删除无用依赖
- 统一代码风格
- 更新过时文档

**策略三：自动化检查**

在CICD流水线中加入"熵检查"

- 代码重复率检查
- 依赖数量检查
- 圈复杂度检查
- 测试覆盖率检查

当这些指标超过阈值时

自动告警

提醒团队进行"减熵"

**策略四：Spec同步**

每次代码变更后

同步更新Spec

确保Spec与实现始终一致

这是防止"Spec腐化"的关键

### 2.3 熵管理的度量

要管理熵

首先要能度量熵

我们团队使用的"熵指标"

| 指标 | 健康阈值 | 告警阈值 | 检查频率 |
|------|----------|----------|----------|
| 代码重复率 | <3% | >5% | 每次提交 |
| 依赖数量 | 稳定 | 周增长>3 | 每周 |
| 圈复杂度 | <10 | >15 | 每次提交 |
| 测试覆盖率 | >80% | <70% | 每次提交 |
| Spec一致性 | 100% | <95% | 每次提交 |
| 文档同步率 | >90% | <80% | 每周 |

这些指标

不需要人工统计

全部由CICD流水线自动计算

超过告警阈值时

自动创建"减熵"任务

## 3. 上下文大于一切

在Harness Coding中

有一句话我反复强调

**上下文大于一切**

什么是上下文

上下文是Agent在执行任务时

能获取到的所有相关信息

包括

- Rules：项目规则和约束
- Skills：可复用的能力定义
- MCPs：外部工具和数据源
- Memories：历史经验和知识
- Spec：当前任务的契约
- 代码库：现有代码和结构

Agent的输出质量

直接取决于上下文的质量

**垃圾上下文 → 垃圾输出

优质上下文 → 优质输出**

这是Harness Coding中最基本的因果关系

### 3.1 上下文的三个层次

| 层次 | 内容 | 作用范围 | 注入方式 |
|------|------|----------|----------|
| 全局上下文 | Rules、Design Token、项目约定 | 所有任务 | 自动加载 |
| 任务上下文 | Spec、相关代码、相关测试 | 当前任务 | 按需注入 |
| 历史上下文 | Memories、过往经验、教训 | 相似任务 | 查询注入 |

全局上下文是"常识"

每个Agent都应该知道

任务上下文是"专业知识"

只有执行相关任务的Agent需要

历史上下文是"经验"

通过记忆系统按需查询

### 3.2 上下文污染

上下文不是越多越好

过多的上下文会导致"上下文污染"

表现为

- 重要信息被淹没在大量无关信息中
- Agent的注意力被分散
- Token成本增加但效果下降
- 相互矛盾的规则让Agent无所适从

所以上下文管理的核心

**不是"给Agent更多信息"

而是"给Agent最相关的信息"**

我们团队的做法

- 全局上下文控制在2000 Token以内
- 任务上下文按需注入，不贪多
- 历史上下文通过向量检索，只取Top-K
- 定期清理过时的Rules和Memories

### 3.3 上下文的生命周期管理

上下文不是"设置一次就不管了"

它有自己的生命周期

**创建**

- 新的Rules在项目初期创建
- 新的Skills在首次遇到特定场景时创建
- 新的Memories在任务完成后存储

**维护**

- Rules随项目演进定期更新
- Skills在发现更好实践时迭代
- Memories在发现冲突时合并

**清理**

- 过时的Rules及时删除
- 不再使用的Skills归档
- 错误的Memories删除

这个生命周期管理

就是ISIER架构中Refl反思层的核心工作

**反思的本质

就是上下文的生命周期管理**

### 3.4 上下文的版本化

我们团队的做法

把所有上下文（Rules、Skills、Memories）

都纳入版本管理

每次变更都有

- 版本号
- 变更原因
- 变更内容
- 变更人

这样当Agent的输出突然变差时

你可以回溯"是哪次上下文变更导致的"

并快速回滚到之前的版本

上下文版本化

是Harness环境"可回滚"的基础

## 4. 持续进化的秘籍

最后一节

来聊聊Harness环境持续进化的"秘籍"

其实没有什么秘籍

就是两个词

**反馈和迭代**

### 4.1 反馈闭环

Harness环境的进化

依赖于一个完整的反馈闭环

```
任务执行 → 发现问题 → 分析根因 → 更新上下文 → 下次任务执行更好
```

这个闭环的关键

是"发现问题"这一步不能跳过

每次任务完成后

必须问自己

- Agent的输出是否符合预期？
- 有没有返工？返工的原因是什么？
- Spec是否足够清晰？
- Rules是否被正确遵守？
- 有没有新的模式可以沉淀为Skill？

这些问题

就是Refl反思层的具体内容

### 4.2 迭代的节奏

进化不是"想到就改"

而是有节奏的迭代

我们团队的迭代节奏

| 节奏 | 内容 | 参与者 |
|------|------|--------|
| 每次任务 | 存储Memory、记录教训 | 任务执行者 |
| 每日 | 快速回顾当天的返工和问题 | 全员 |
| 每周 | 更新Rules和Skills | Harness架构师 |
| 每两周 | 技术债清理 + 上下文清理 | 全员 |
| 每月 | Harness环境全面Review | 全员 |

这个节奏

保证了"小问题及时修

大问题定期修"

而不是"积攒到无法忍受了再大改"

### 4.3 进化的方向

Harness环境的进化

应该朝以下方向

**更精确的约束**

Rules从"模糊的指导"进化为"精确的规则"

比如从"代码要整洁"

进化为"函数不超过50行，参数不超过4个"

**更丰富的Skills**

从"通用Skill"进化为"场景化Skill"

比如从"前端开发Skill"

进化为"ListPage开发Skill"、"FormPage开发Skill"

**更智能的记忆**

从"无差别的记忆存储"进化为"分类的记忆管理"

比如区分"经验记忆"、"偏好记忆"、"事实记忆"

按需检索，避免污染

**更自动化的流程**

从"人工触发反思"进化为"自动触发反思"

Agent完成任务后自动执行反思流程

自动更新上下文

人工只做审核

### 4.4 进化的陷阱

**陷阱一：过度优化**

不要为了"进化"而频繁修改Rules和Skills

每次修改都有成本

包括Agent需要重新适应

团队需要重新学习

所以

**只在有明确收益时才修改**

**陷阱二：忽视人的进化**

Harness环境的进化

不只是Rules和Skills的进化

更是"人"的进化

团队成员需要

- 学习新的Spec编写技巧
- 提升判断力和决策力
- 理解新的Agent行为模式
- 适应新的工作流程

如果只进化Harness而不进化人

Harness的进化就会停滞

**陷阱三：盲目模仿**

别人的Harness环境

不一定适合你

每个团队的

业务领域、技术栈、团队规模、工作习惯

都不同

所以

**参考别人的经验

但构建自己的Harness**

## 结语

自我进化是Harness Coding中

最"玄学"但最重要的环节

它不像编码那样有明确的输入输出

不像测试那样有明确的通过失败

不像运维那样有明确的指标告警

它更像是一种"习惯"

一种"持续改进的习惯"

熵管理让你保持清醒

上下文管理让你保持聚焦

反馈闭环让你保持进步

定期迭代让你保持稳定

这些加在一起

就是Harness环境"持续进化"的全部秘密

**没有银弹

只有日复一日的打磨**
