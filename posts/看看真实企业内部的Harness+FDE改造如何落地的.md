## 1. 一次完整的Harness内部落地流程

![ISIER完整落地流程](https://res.cloudinary.com/isieghiq/image/upload/v1787990312/harnesscraft/3167ad18b8582e03236f70c1f209133923aa5328.png)


这一节

我用一个真实的例子

来展示一次完整的Harness内部落地流程

从需求到上线

从Intent到Refl

### 1.1 需求背景

假设我们需要开发一个"用户反馈"功能

用户可以在产品内提交反馈

包括文字描述和截图

管理员可以在后台查看和处理反馈

这是一个中等复杂度的功能

涉及前端、后端、数据库、文件存储

### 1.2 Intent层 — 意图识别

**输入**：用户的原始描述

> "我想加一个反馈功能，用户能提交反馈，后台能查看和管理"

**Agent的意图识别**：

1. 核心需求：用户提交反馈 + 管理员管理反馈
2. 模糊点：反馈是否支持图片？是否需要分类？是否需要回复？
3. 与用户确认模糊点

**确认结果**：

- 反馈支持文字 + 截图（最多3张）
- 反馈需要分类（Bug、建议、咨询）
- 管理员可以回复反馈
- 反馈状态：待处理、处理中、已回复、已关闭

**输出**：已确认的意图声明

### 1.3 Spec层 — 契约生成

**Spec文档**：

```
## 用户反馈功能 Spec

### 接口定义
- POST /api/feedback — 提交反馈
- GET /api/feedback — 反馈列表（管理员）
- GET /api/feedback/:id — 反馈详情
- POST /api/feedback/:id/reply — 回复反馈
- PUT /api/feedback/:id/status — 更新状态

### 数据模型
- Feedback: id, userId, category, content, images, status, createdAt
- FeedbackReply: id, feedbackId, adminId, content, createdAt

### 业务规则
- 普通用户只能提交和查看自己的反馈
- 管理员可以查看所有反馈
- 图片上传限制：单张<2MB，最多3张
- 分类：bug(缺陷)、suggestion(建议)、question(咨询)

### 验收标准
- [ ] 用户可提交文字+图片反馈
- [ ] 管理员可查看反馈列表（支持筛选和分页）
- [ ] 管理员可回复反馈
- [ ] 反馈状态可更新
- [ ] 图片上传有大小和数量限制
- [ ] 权限控制正确

### 回滚方案
- 回滚触发：核心流程不可用或数据异常
- 回滚方式：还原数据库Schema + 回退代码版本
- 数据库兼容：新增表，不影响现有表
```

**Plan文档**：

```
## 实现计划

### 阶段1：后端（预计2小时）
1. 数据库迁移（新建feedback和feedback_reply表）
2. 实现5个API接口
3. 实现文件上传（图片存储到OSS）
4. 编写单元测试和集成测试

### 阶段2：前端（预计2小时，与后端并行）
1. 反馈提交页面（表单+图片上传）
2. 反馈列表页面（表格+筛选+分页）
3. 反馈详情页面（详情+回复）
4. 编写组件测试

### 阶段3：集成（预计1小时）
1. 前后端联调
2. E2E测试
3. 部署Staging验证
```

**用户确认**：用户审核Spec和Plan → 确认通过

### 1.4 Impl层 — 执行

**上下文注入**：

- 加载Rules：代码规范、安全规范、API设计规范
- 激活Skills：后端开发Skill、前端开发Skill、测试Skill
- 注入Memories：类似功能的实现经验

**并行执行**：

- 后端Agent：按Spec实现API和数据库
- 前端Agent：按Spec实现页面和组件
- 测试Agent：按Spec生成测试用例

**ReAct修正**：

- 后端Agent发现图片上传需要OSS配置 → 查询Memory → 找到OSS配置经验 → 正确实现
- 前端Agent发现反馈表单需要图片预览 → 查询Skill → 使用已有的Upload组件 → 正确实现

**冒烟测试**：

- 提交反馈 → 成功
- 查看列表 → 成功
- 回复反馈 → 成功

### 1.5 Eval层 — 验收

**自动验证**：

- 单元测试：12个用例全部通过
- 集成测试：5个用例全部通过
- 覆盖率：87%
- 性能：接口平均响应45ms

**人工验收**：

- [x] 核心流程走通
- [x] 图片上传限制生效
- [x] 权限控制正确
- [ ] 反馈列表的筛选交互不够流畅（反馈）

**反馈处理**：

- 筛选交互问题 → 反哺Spec → 补充筛选交互细节 → Agent重新实现 → 验收通过

### 1.6 Refl层 — 反思

**上下文更新**：

- 新增Skill：FeedbackPage开发Skill（沉淀反馈页面的布局模式）
- 更新Memory：图片上传组件的复用经验

**版本归档**：

- 归档Spec文档（v1.0）
- 归档实现代码（commit hash）
- 归档测试报告

**Harness环境完善**：

- 发现"筛选交互"是常见遗漏点 → 在前端Skill中补充"列表页筛选交互检查清单"

**记忆存储**：

- 存储经验：反馈功能的实现模式和常见问题
- 存储事实：OSS配置方式
- 存储偏好：用户对筛选交互的偏好

### 1.7 全流程耗时

| 阶段 | 耗时 | 人工参与 |
|------|------|----------|
| Intent | 15分钟 | 确认意图 |
| Spec | 30分钟 | 审核Spec和Plan |
| Impl | 3小时 | 监控进度 |
| Eval | 30分钟 | 人工验收 |
| Refl | 15分钟 | 审核反思 |
| 总计 | 约4.5小时 | 约1.5小时 |

人工实际参与时间约1.5小时

其余3小时是Agent在"后台"执行

人在此期间可以做其他任务的Spec或验收

## 2. 0到1如何落地

上一节展示了一次功能开发的完整流程

这一节

来聊一个更大的话题

**一个项目从0到1如何落地Harness Coding**

### 2.1 第一步：搭建Harness环境

在写第一行代码之前

先搭建Harness环境

这是最重要的一步

也是最容易跳过的一步

最小可用Harness环境

```
.devin/
├── rules/
│   ├── coding-standards.md    # 代码规范
│   ├── api-design.md          # API设计规范
│   └── fallback-first.md      # 回滚原则
├── skills/
│   ├── task-execution/         # 任务执行流程
│   └── image-gen/              # 图片生成（可选）
└── AGENTS.md                   # 项目说明
```

这个最小环境

定义了"代码怎么写"、"接口怎么设计"、"出错怎么办"

有了它

Agent的产出就有了基本约束

### 2.2 第二步：定义项目结构

不要让Agent自由决定项目结构

你需要在Spec中明确定义

```
project/
├── frontend/           # 前端
│   ├── src/
│   │   ├── components/ # 基础组件
│   │   ├── pages/      # 页面
│   │   ├── services/   # API调用
│   │   └── styles/     # 全局样式
│   └── package.json
├── backend/            # 后端
│   ├── src/
│   │   ├── modules/    # 业务模块
│   │   ├── common/     # 公共组件
│   │   └── config/     # 配置
│   └── go.mod
├── deploy/             # 部署
│   ├── docker-compose.yml
│   └── nginx.conf
└── .devin/             # Harness环境
```

这个结构

让Agent知道"代码应该放在哪里"

避免"到处乱放"

### 2.3 第三步：先做核心功能

0到1阶段

不要追求"功能完整"

而是追求"核心功能可用"

什么是核心功能

就是如果这个功能没有

产品就完全无法使用的那个功能

比如

- 电商网站的核心功能是"下单"
- SaaS产品的核心功能是"登录 + 核心业务流程"
- 内容平台的核心功能是"发布 + 浏览"

先让核心功能跑通

再逐步添加其他功能

### 2.4 第四步：建立CICD

核心功能跑通后

立即建立CICD流水线

不要等"功能做完了再搭CICD"

因为越早建立CICD

越早能自动化验证

越早能自动部署

越早能发现问题

最小CICD流水线

1. 代码提交 → 自动构建
2. 构建成功 → 自动测试
3. 测试通过 → 自动部署Staging
4. 人工验收 → 部署生产

### 2.5 第五步：迭代

0到1不是终点

而是起点

上线后

根据用户反馈持续迭代

每次迭代都走ISIER流程

每次迭代都更新Harness环境

每次迭代都积累Memories

**0到1靠"搭基础"

1到多靠"持续迭代"**

## 3. 1到多如何重构

当项目从1个产品扩展到多个产品时

Harness环境也需要"重构"

### 3.1 什么时候需要重构

以下信号出现时

说明你的Harness环境需要重构

- 不同的产品共用同一套Rules，但规则互相冲突
- 一个项目的Skill在另一个项目不适用
- Memories中积累了大量不相关的经验
- Agent的产出质量在不同产品间差异很大
- 团队成员对Harness环境的理解不一致

### 3.2 重构策略

**策略一：按产品线拆分**

```
.devin/
├── shared/              # 跨产品共享
│   ├── rules/           # 通用规则
│   └── skills/          # 通用Skill
├── product-a/           # 产品A专属
│   ├── rules/
│   └── skills/
└── product-b/           # 产品B专属
    ├── rules/
    └── skills/
```

通用规则（如代码规范、安全规范）放在shared

产品专属规则（如业务逻辑、领域约定）放在各自目录

**策略二：Memories分类**

按产品线分类存储Memories

避免跨产品的经验污染

**策略三：Spec模板化**

不同产品的Spec模板不同

为每个产品线定制Spec模板

提高Spec编写效率

### 3.3 重构的回滚

重构本身也需要回滚方案

- 重构前备份整个.devin目录
- 重构后在小范围验证
- 确认无问题后再全面切换
- 保留旧环境一周作为兜底

## 4. 团队管理

![团队标准对比](https://res.cloudinary.com/isieghiq/image/upload/v1787990300/harnesscraft/da76e87a66ddf4a49c0e4f3956250ebfab978cc6.png)


Harness Coding模式下的团队管理

跟传统模式有很大不同

### 4.1 招聘标准的变化

| 传统招聘标准 | Harness招聘标准 |
|-------------|----------------|
| 熟悉XX框架 | 系统设计能力 |
| 编码速度快 | Spec编写能力 |
| 算法能力强 | 判断力和决策力 |
| 项目经验多 | Harness经验（可培养） |
| 能独立开发 | 能独立决策 |

简单来说

招"能判断"的人

而不是"能编码"的人

### 4.2 绩效评估的变化

传统模式下

评估"写了多少代码"

Harness模式下

评估"做了多少正确的决策"

| 评估维度 | 传统指标 | Harness指标 |
|----------|----------|-------------|
| 产出 | 代码行数 | 功能交付数 |
| 质量 | Bug率 | 返工率 |
| 效率 | 开发周期 | Spec到上线周期 |
| 协作 | Code Review数 | Spec Review数 |
| 成长 | 新技术学习 | Harness环境贡献 |

### 4.3 团队文化的建立

Harness Coding团队需要的文化

**透明**

所有Spec、Rules、Skills对全员可见

任何人都可以提出修改建议

**克制**

不追求"更多功能"

追求"更正确的功能"

**反馈**

每次任务完成后必须反思

每个问题都必须有改进措施

**信任**

信任Agent的执行能力

信任团队成员的判断能力

## 5. 市场调研

即使是技术团队

也不能忽视市场调研

因为

**做出来的东西没人用

技术再好也是白费**

### 5.1 Harness Coding下的市场调研

用Agent加速市场调研

| 调研环节 | 传统方式 | Harness方式 |
|----------|----------|-------------|
| 竞品分析 | 人工收集整理 | Agent自动收集和分析 |
| 用户访谈 | 人工设计问题 | Agent辅助设计+分析 |
| 落地页测试 | 人工开发 | Agent快速生成+部署 |
| 数据分析 | 人工统计 | Agent自动分析+可视化 |

### 5.2 调研的核心原则

**快**

用Harness Coding快速出原型

快速投入市场测试

不要花几个月做调研报告

**真**

观察用户的真实行为

而不是用户的口头反馈

**小**

从小范围开始

先验证核心假设

再扩大验证范围

## 6. 对OPC和AI创业公司的忠告

最后一节

写给OPC（一人公司）和AI创业公司

### 6.1 给OPC的忠告

**忠告一：你是指挥官，不是执行者**


作为OPC

你最大的优势不是"什么都会"

而是"能指挥AI做任何事"

把执行交给Agent

把判断留给自己

**忠告二：先建Harness，再写代码**

不要急于开发

先花一周时间搭建Harness环境

这一周的"投资"

会在后续几个月持续回报

**忠告三：克制功能，聚焦核心**

一个人能做的事有限

不要追求"功能大而全"

把一个核心功能做到极致

比做十个半成品更有价值

**忠告四：善用免费额度**

OPC的预算有限

善用各工具的免费额度

用多工具组合降低成本

能白嫖绝不花钱

### 6.2 给AI创业公司的忠告

**忠告一：Harness是核心资产**

你的代码可以被抄

你的产品可以被抄

但你的Harness环境

是团队在长期实践中积累的

包含了你们的经验、教训和最佳实践

这是别人抄不走的

**忠告二：不要过度依赖单一工具**

今天好用的工具

明天可能涨价或停服

保持工具的多样性

建立"可切换"的Harness环境

**忠告三：人的成长比Harness的成长更重要**

Harness环境可以快速搭建

但"能用好Harness的人"需要长期培养

投资团队成员的成长

是AI创业公司最重要的投资

**忠告四：保持技术敏感度**

AI领域变化极快

今天的最佳实践

明天可能就过时了

保持学习

保持尝试新工具和新方法

**但不要盲目追新

只在有明确收益时才切换**
