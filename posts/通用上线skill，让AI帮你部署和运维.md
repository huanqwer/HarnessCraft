## 1. CICD还有必要吗？

![Harness CICD标准流程](https://res.cloudinary.com/isieghiq/image/upload/v1787990268/harnesscraft/66624bfbebf1c9b0c2dd1410fc6c4916d61ff526.png)


每次讲到运维

总有人问我一个问题

"AI都能自动写代码、自动部署了

CICD还有必要吗？"

我的回答是

**不仅有必要，而且比以前更重要了**

原因很简单

CICD的流水线速度

直接决定了Harness Coding的迭代速度

在传统开发中

一个开发者一天可能只提交两三次代码

CICD的压力不大

但在Harness Coding中

Agent可能在一天内生成几十次甚至上百次代码变更

如果没有自动化的CICD流水线

你根本来不及验证这些变更

### 1.1 CICD在Harness Coding中的新角色

在传统开发中

CICD的主要作用是

- 自动化构建
- 自动化测试
- 自动化部署

在Harness Coding中

CICD的角色升级了

它不仅是"自动化"

更是"守门员"

| 传统CICD | Harness CICD |
|----------|-------------|
| 构建代码 | 构建代码 + 验证Spec一致性 |
| 跑测试 | 跑测试 + 覆盖率检查 |
| 部署到服务器 | 部署 + 自动冒烟测试 |
| 人工确认上线 | 自动灰度 + 自动回滚 |

最大的变化是

Harness CICD不仅要验证"代码能不能跑"

还要验证"代码是否符合Spec"

因为Agent生成的代码

可能在功能上是对的

但在实现上偏离了Spec的约束

比如Spec要求"密码必须加密存储"

但Agent可能用了明文存储

功能上"注册"是通的

但安全要求没满足

所以CICD流水线中

需要加入"Spec一致性检查"的环节

### 1.2 Harness CICD的标准流程

我们团队的CICD标准流程

1. **代码提交**：Agent生成代码后自动提交
2. **Spec检查**：验证代码是否符合Spec定义的接口和约束
3. **单元测试**：执行Agent生成的单元测试
4. **集成测试**：验证模块间接口协作
5. **安全扫描**：检查依赖漏洞、敏感信息泄露
6. **构建镜像**：打包Docker镜像
7. **部署Staging**：自动部署到预发环境
8. **冒烟测试**：在Staging上执行核心流程验证
9. **人工审批**：人工确认后才能部署生产
10. **灰度发布**：先灰度10%流量，观察指标
11. **全量发布**：指标正常则全量发布
12. **自动回滚**：指标异常则自动回滚

这个流程的关键是

**步骤9之前全自动

步骤9需要人工

步骤10-12自动执行但有人工兜底**

### 1.3 CICD的Harness化

CICD本身也可以Harness化

我们团队用Agent管理CICD的方式

| Agent | 职责 |
|-------|------|
| Pipeline Agent | 维护CICD配置，根据项目变化自动更新流水线 |
| Test Agent | 根据Spec自动生成测试代码并加入流水线 |
| Deploy Agent | 执行部署操作，管理灰度策略 |
| Monitor Agent | 监控部署后的指标，判断是否需要回滚 |

这些Agent协同工作

让CICD从"配置一次然后手动触发"

变成"自动适应项目变化并持续运行"

## 2. 守住AI部署的安全红线

AI在运维环节最大的风险

不是它做错了什么

而是它做了"你没想到的事"

### 2.1 AI部署的典型风险

| 风险类型 | 具体表现 | 后果 |
|----------|----------|------|
| 敏感信息泄露 | Agent把密钥写进配置文件或日志 | 密钥被窃取 |
| 权限过度 | Agent申请了超出需要的权限 | 越权操作 |
| 依赖不可信 | Agent引入了未审核的第三方依赖 | 供应链攻击 |
| 配置漂移 | Agent修改了线上配置但未记录 | 配置不一致 |
| 端口暴露 | Agent开放了不必要的端口 | 攻击面扩大 |

这些风险的共同点是

Agent在做的时候

它认为这是"完成任务所必需的"

但从安全角度看

这些操作都是高风险的

### 2.2 安全红线

我们团队制定了以下安全红线

Agent在部署环节**绝对不允许**做的事情

- ❌ 直接操作生产数据库（必须有审批流程）
- ❌ 在代码或配置中硬编码密钥（必须用环境变量或密钥管理服务）
- ❌ 开放非必要的端口（默认只开放80和443）
- ❌ 使用未审核的第三方依赖（必须经过安全扫描）
- ❌ 跳过Staging直接部署生产（必须先通过Staging验证）
- ❌ 关闭防火墙或安全组规则（必须通过审批修改）

这些红线

不是写在文档里"提醒"Agent

而是硬编码在CICD流水线中

作为自动检查的规则

如果Agent的产出触发了任何一条红线

流水线自动中断

不允许继续

**安全红线不是建议，而是强制约束**

### 2.3 最小权限原则

在Harness Coding的运维中

最小权限原则比以往更重要

因为Agent的"自主性"很强

如果给它过大的权限

它可能在"不知不觉"中做了危险的操作

我们团队的做法

- CICD Agent只有Staging环境的写权限
- 生产环境的写权限需要人工审批后临时授予
- 数据库操作通过专门的DB Agent执行
- 所有操作都有审计日志
- 权限按需授予，任务完成后自动回收

这样即使Agent"想"做危险操作

它也没有权限去做

## 3. 一定要"回滚优先"

在Harness Coding的运维中

有一个原则被放在最高优先级

**回滚优先**

这个原则跟我们在ISIER架构中的Rollback横切原则一脉相承

但在运维层面

它有更具体的含义

### 3.1 为什么回滚优先

在传统运维中

当线上出现问题时

第一反应通常是"修复"

找到bug → 修复代码 → 重新部署

但在Harness Coding中

由于代码是Agent生成的

"找到bug"这个过程可能很耗时

因为你需要先理解Agent生成的代码

然后定位问题

然后修复

这个过程可能需要几十分钟甚至几个小时

而在这段时间里

线上服务是异常的

用户是受影响的

所以Harness Coding运维的第一原则

**不是"修复"

而是"回滚"**

先回滚到上一个稳定版本

恢复服务

然后再慢慢排查和修复

### 3.2 回滚的三个层次

| 层次 | 触发条件 | 执行方式 | 恢复时间 |
|------|----------|----------|----------|
| L1 自动回滚 | 监控指标异常 | CICD流水线自动执行 | 秒级 |
| L2 灰度回滚 | 灰度期间发现问题 | 自动停止灰度，保持旧版本 | 秒级 |
| L3 手动回滚 | 人工判断需要回滚 | 人工触发回滚命令 | 分钟级 |

L1和L2是自动的

依赖监控指标和自动判断

L3是人工的

用于处理"指标正常但人有疑虑"的场景

### 3.3 回滚的前提条件

回滚不是"想回就回"

它需要以下前提条件

- **版本可追溯**：每次部署都有唯一版本号，可以精确回滚到任意版本
- **数据库兼容**：回滚后的代码与当前数据库状态兼容（这是最难的部分）
- **配置可回滚**：配置变更也要版本化，可以回滚
- **回滚已验证**：回滚操作本身也要经过测试，确保能成功执行

其中数据库兼容是最容易被忽视的

如果新版本做了数据库Schema变更

直接回滚到旧版本可能导致旧代码无法读取新Schema

所以数据库变更必须保证**向后兼容**

即

新代码能读旧Schema

旧代码也能读新Schema

这要求

- 新增字段必须有默认值
- 删除字段必须分两步（先停止使用，下个版本再删除）
- 类型变更必须通过新增字段过渡

### 3.4 回滚方案模板

在ISIER的Spec阶段

每次变更都必须附带回滚方案

回滚方案的标准模板

```
## 回滚方案

### 回滚触发条件
- [条件1]
- [条件2]

### 回滚步骤
1. 执行回滚命令：[具体命令]
2. 验证服务恢复：[验证方法]
3. 通知相关人员：[通知方式]

### 回滚验证
- [ ] 核心功能可用
- [ ] 数据一致性正常
- [ ] 监控指标恢复

### 数据库回滚
- 是否需要回滚数据库：是/否
- 回滚方式：[具体方式]
- 数据兼容性：[说明]
```

这个模板

不是可选的

而是每次变更的**必须项**

没有回滚方案的变更

不允许进入CICD流水线

## 4. 可观测、可验证、可回滚

![运维三原则闭环](https://res.cloudinary.com/isieghiq/image/upload/v1787990436/harnesscraft/04eb8a3ef0a5278945c20a9e433be0c6b7574422.png)


这三个词

是Harness Coding运维的三大支柱

我把它们称为"运维三原则"

### 4.1 可观测

可观测是基础

如果你看不到系统的状态

你就无法判断是否需要回滚

也无法判断回滚是否成功

可观测的三个维度

**日志**

- 结构化日志（JSON格式）
- 统一的TraceID贯穿全链路
- 敏感信息脱敏
- 日志保留策略（热数据7天，冷数据90天）

**指标**

- 黄金四指标：延迟、流量、错误率、饱和度
- 按接口维度聚合
- 设置告警阈值
- 保留历史趋势用于对比

**链路追踪**

- 每个请求有唯一TraceID
- 跨服务调用链可追踪
- 数据库查询耗时可见
- 外部依赖调用可见

在Harness Coding中

可观测性不是"事后添加"的

而是在Spec阶段就定义好的

Agent在实现代码时

必须同时实现日志、指标和链路追踪

### 4.2 可验证

可验证是信心来源

如果你无法验证系统的正确性

你就无法放心地部署

也无法放心地回滚

可验证的三个层次

**部署前验证**

- 单元测试通过
- 集成测试通过
- 安全扫描通过
- Spec一致性检查通过

**部署中验证**

- Staging环境冒烟测试通过
- 灰度期间指标正常
- 人工验收通过

**部署后验证**

- 核心接口可用性检查
- 关键业务流程走查
- 监控指标对比基线
- 用户反馈收集

每个层次的验证

都有明确的通过标准

不通过就不进入下一阶段

### 4.3 可回滚

可回滚是安全底线

如果你无法回滚

那每一次部署都是一次"赌博"

可回滚的三个要求

**技术上可回滚**

- 版本管理完善
- 数据库向后兼容
- 配置版本化
- 回滚命令已验证

**流程上可回滚**

- 回滚方案已定义
- 回滚权限已配置
- 回滚审批流程已明确
- 回滚通知机制已建立

**文化上可回滚**

- 回滚不被视为"失败"
- 回滚是正常操作
- 不追责，只复盘
- 鼓励"宁可回滚也不要冒险"

### 4.4 三原则的关系

这三个原则不是独立的

它们形成了一个闭环

```
可观测 → 发现问题 → 可验证 → 确认问题 → 可回滚 → 恢复服务 → 可观测 → 验证恢复
```

如果缺少任何一个环节

这个闭环就会断裂

- 没有可观测：你不知道出了问题
- 没有可验证：你不确定是否真的出了问题
- 没有可回滚：你知道出了问题但无法恢复

所以这三个原则

是缺一不可的

**它们共同构成了Harness Coding运维的安全网**

## 结语

运维在Harness Coding中

可能是最"保守"的环节

在编码环节

我们鼓励AI大胆尝试

在测试环节

我们让AI自主执行

但在运维环节

我们要求AI"谨慎再谨慎"

因为运维的每一次操作

都直接影响线上服务

都直接影响真实用户

都直接影响业务收入

所以

**编码可以激进

运维必须保守**


CICD自动化 + 安全红线 + 回滚优先 + 可观测/可验证/可回滚

这四样东西

就是Harness Coding运维的全部核心

它们不是"建议"

而是"底线"

触碰底线的事情

无论AI多么"自信"

都不允许执行
