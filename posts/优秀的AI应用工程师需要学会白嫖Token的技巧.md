## 1. 我们是如何进行开发工作的

![5人团队产能对比](https://res.cloudinary.com/isieghiq/image/upload/v1787990238/harnesscraft/2d182cc9680b026d4d73cecb252d7177a9adb474.png)


在聊具体的成本控制策略之前

我想先介绍一下我们团队的实际工作方式

因为成本控制不是"省钱"

而是"用最少的资源产出最大的价值"

所以理解我们的工作方式

是理解成本控制的前提

### 1.1 5人团队，0手写代码

我们团队5个人

没有一个人写代码

所有代码由Agent在Harness架构下生成

这5个人的分工

| 角色 | 人数 | 核心职责 |
|------|------|----------|
| Harness架构师 | 1 | 设计和维护Harness环境（Rules、Skills、MCPs） |
| 产品经理 | 1 | 需求分析、Spec编写、市场验证 |
| 后端指挥官 | 1 | 后端Spec审核、架构决策、验收 |
| 前端指挥官 | 1 | 前端Spec审核、UI设计语言、验收 |
| 运维指挥官 | 1 | CICD、部署、监控、回滚 |

注意

这里没有"开发者"

因为开发工作由Agent完成

人的角色是"指挥官"

负责判断、决策和验收

### 1.2 一天的工作流程

我们一天的工作大致是这样的

**上午（9:00-12:00）**

- 产品经理梳理当天需求，编写Spec
- 各指挥官审核Spec，确认验收标准
- 启动Agent执行任务（多任务并行）

**下午（13:00-18:00）**

- Agent执行期间，指挥官监控进度
- Agent完成后，指挥官进行验收
- 不通过的反馈给Agent重新执行
- 通过的进入CICD流水线

**晚上（18:00-20:00）**

- CICD自动部署到Staging
- 冒烟测试通过后人工验收
- 确认无误后灰度发布
- 运维指挥官监控灰度指标

这个流程的关键是

**Agent在"后台"持续工作

人在"前台"做判断和决策**

人不是在"等"Agent

而是在Agent工作的同时

做其他任务的Spec或验收

这样人的时间利用率非常高

### 1.3 为什么这样能省钱

这种工作方式的成本优势

| 对比项 | 传统5人团队 | 我们的5人团队 |
|--------|-------------|---------------|
| 代码产出 | 5人手写 | Agent生成，5人指挥 |
| 日均代码量 | 约2000行 | 约10000行 |
| 返工率 | 约30% | 约15% |
| 人力成本 | 5人薪资 | 5人薪资（相同） |
| 工具成本 | 接近0 | 约$200-500/月 |
| 服务器成本 | 约$500/月 | 约$200/月（见第4节） |

人力成本相同

但产出是5倍

返工率减半

这就是Harness Coding的成本优势

**不是通过降低人力成本来省钱

而是通过提高人力效率来摊薄单位成本**

## 2. 我们是如何选择模型的

![模型选型矩阵](https://res.cloudinary.com/isieghiq/image/upload/v1787990253/harnesscraft/3448e2f8d5c8474516b7b635475311b28075fdf9.png)


模型选择是Harness Coding成本控制的核心

因为Token成本是最大的可变成本

选对模型

可能帮你省掉80%的Token费用

选错模型

可能让你多花几倍的钱

### 2.1 模型选择的三个维度

| 维度 | 说明 | 权重 |
|------|------|------|
| 能力 | 模型能否胜任当前任务 | 最高 |
| 价格 | 模型的Token单价 | 高 |
| 速度 | 模型的响应速度 | 中 |

我们团队的原则

**能力够用就行，不追求最强

价格越低越好，但不牺牲能力

速度重要但不致命**

### 2.2 按任务类型选模型

不同类型的任务

对模型能力的要求不同

所以用不同的模型

| 任务类型 | 推荐模型 | 原因 |
|----------|----------|------|
| 需求分析、Spec生成 | 顶级模型（Opus/GPT-4） | 需要强推理和结构化能力 |
| 后端代码生成 | 中高端模型（Sonnet/GPT-4o） | 代码生成能力足够，性价比高 |
| 前端代码生成 | 中端模型（Sonnet/4o-mini） | 前端复杂度通常低于后端 |
| 测试代码生成 | 中端模型 | 测试代码模式固定，不需要最强模型 |
| 文档生成 | 中低端模型 | 文档不需要复杂推理 |
| 代码审查 | 中高端模型 | 需要理解代码逻辑和发现潜在问题 |
| 运维脚本 | 中端模型 | 脚本通常简单且模式化 |

这个分配的核心思想

**把贵的模型用在刀刃上

把便宜的模型用在重复劳动上**

### 2.3 模型切换的自动化

在Harness Coding中

模型切换不应该是手动的

而应该是自动的

我们的做法

在Skill中定义每个任务类型使用的默认模型

Agent在执行任务时

自动选择对应的模型

如果任务复杂度超出预期

Agent可以"升级"到更强的模型

但需要说明升级理由

这样既保证了成本控制

又保证了灵活性

### 2.4 模型选择的误区

**误区一：永远用最强模型**

很多人觉得"反正AI写代码比我快

用最强的模型保证质量"

但最强模型的Token成本可能是中端模型的10倍

而代码质量只好了10%

这笔账不划算

**误区二：永远用最便宜的模型**

另一个极端是"用最便宜的模型省钱"

但便宜模型的代码质量差

返工率高

返工的Token成本 + 人工验收成本

可能比直接用好模型更高

**误区三：不关注模型更新**

模型市场变化很快

每个月都有新模型发布

价格也在不断调整

上个月性价比最高的模型

这个月可能已经被超越了

所以需要持续关注

## 3. 时刻关注官方政策，能白嫖绝不花钱


这一节可能是整本书最"实用"的一节

因为它直接关系到你每个月要掏多少钱

### 3.1 各工具的免费额度

截至2026年8月

主流工具的免费/低价额度

| 工具 | 免费额度 | 备注 |
|------|----------|------|
| Claude Code | 免费层有限 | Pro $20/月含较多额度 |
| Cursor | 免费层有限 | Pro $20/月 |
| Windsurf | 免费层较慷慨 | Pro $15/月 |
| Codex | 免费层有限 | Plus $20/月 |
| Gemini | 免费层较慷慨 | Code Assist免费 |

注意

这些额度会随时间变化

**不要记住具体数字

而是记住"去查"这个动作**

### 3.2 白嫖策略

我们的"白嫖"策略

**策略一：多工具组合**

不同工具有不同的免费额度

简单的任务用免费额度大的工具

复杂的任务用能力强的工具

通过工具切换

最大化免费额度的利用

**策略二：关注官方活动**

各家厂商经常推出限时活动

免费额度提升、新用户优惠、教育优惠等

关注官方博客和社交媒体

及时薅羊毛

**策略三：利用开源模型**

对于不敏感的任务

可以使用开源模型（如Llama、Qwen等）

通过本地部署或免费API

零成本执行

**策略四：缓存和复用**

Agent的输出可以缓存

相同的Prompt不需要重复调用

我们在Harness中实现了Prompt缓存

相同的Spec片段不重复发送

这一项就节省了约30%的Token

### 3.3 什么时候该花钱

白嫖不等于不花钱

而是"把钱花在刀刃上"

以下场景值得花钱

- **核心业务逻辑**：用最强模型保证质量
- **高并发任务**：用付费API避免限流
- **生产环境**：用付费版保证稳定性和SLA
- **团队协作**：用团队版保证协作效率

以下场景不该花钱

- **探索性任务**：用免费额度试错
- **文档和注释**：用便宜模型生成
- **测试代码**：用中端模型
- **个人学习**：用免费额度

**白嫖的本质

不是"不花钱"

而是"不在不必要的地方花钱"**

## 4. 多个轻量服务器 > 单机高性能

这一节聊的是服务器成本

也是很多团队容易忽视的隐性成本

### 4.1 为什么多个轻量更好

传统思维

买一台高性能服务器

CPU多核、内存大、带宽足

一台搞定所有

但在Harness Coding的运维场景下

多个轻量服务器比单机高性能更好

原因

| 对比项 | 单机高性能 | 多个轻量 |
|--------|-----------|----------|
| 成本 | $200/月 × 1 = $200 | $40/月 × 4 = $160 |
| 单点故障 | 一台挂了全挂 | 一台挂了只影响部分 |
| 扩展性 | 升级要停机 | 加一台即可 |
| 隔离性 | 服务互相影响 | 服务互相隔离 |
| 地域分布 | 单地域 | 多地域部署 |

成本更低

可靠性更高

扩展性更好

何乐而不为

### 4.2 我们的部署架构

我们团队的典型部署架构

| 服务器 | 配置 | 用途 | 月费 |
|--------|------|------|------|
| Server 1 | 2C4G | Nginx + 前端静态资源 | $20 |
| Server 2 | 2C4G | 后端API服务 | $40 |
| Server 3 | 2C4G | 数据库 + 缓存 | $40 |
| Server 4 | 1C2G | 监控 + 日志 + CICD Runner | $20 |
| 总计 | | | $120 |

对比单机方案

| 服务器 | 配置 | 用途 | 月费 |
|--------|------|------|------|
| Server 1 | 8C16G | 全部服务 | $200 |

月费节省$80

而且可靠性更高

### 4.3 轻量服务器的选择标准

选择轻量服务器时

关注以下几个指标

- **CPU**：2核足够大多数服务
- **内存**：4G够用，数据库服务建议8G
- **带宽**：按量计费比固定带宽更划算（低流量场景）
- **地域**：选择离用户最近的地域
- **备份**：必须有自动快照

我们用的几家

| 服务商 | 优势 | 适用场景 |
|--------|------|----------|
| 阿里云轻量 | 国内访问快 | 面向国内用户 |
| 腾讯云轻量 | 性价比高 | 通用 |
| Vultr | 海外节点多 | 面向海外用户 |
| Hetzner | 极致性价比 | 非核心服务 |

## 5. 共事的人贵在精不在于多

最后一节

聊一个不太"技术"但很"成本"的话题

团队规模

### 5.1 为什么人少反而好

在Harness Coding模式下

团队规模的边际收益是递减的

5个人能做的事

10个人不一定能做得更好

反而可能更差

原因

**协调成本指数增长**

5个人的沟通链路是 5×4/2 = 10条

10个人的沟通链路是 10×9/2 = 45条

协调成本增长了4.5倍

但产出只增长了2倍

**Harness环境维护成本**

人越多

对Harness环境的理解差异越大

Rules、Skills、Spec的统一就越难

一个人写的Spec

另一个人可能理解不了

一个人建的Skill

另一个人可能不会用

**决策效率下降**

人越多

决策越慢

而Harness Coding的核心优势是"快"

如果决策环节慢了

Harness的优势就被抵消了

### 5.2 精兵的标准

在Harness Coding团队中

"精兵"的标准跟传统团队不同

| 传统团队标准 | Harness团队标准 |
|-------------|----------------|
| 编码能力强 | 系统设计能力强 |
| 熟悉多种框架 | 熟悉Spec编写 |
| 能独立开发 | 能独立决策 |
| 解决技术问题 | 解决业务问题 |
| 代码质量高 | 判断力强 |

简单来说

传统团队需要"能做事"的人

Harness团队需要"能判断"的人

做事交给Agent

判断交给人

### 5.3 5人团队的黄金比例

根据我们的实践

5人团队是Harness Coding的黄金规模

- 1个产品（需求+Spec+验证）
- 1个后端（架构+Spec+验收）
- 1个前端（设计语言+Spec+验收）
- 1个运维（CICD+部署+监控）
- 1个Harness架构师（Rules+Skills+MCPs）

5个人

5个角色

没有重叠

没有冗余

每个人都是各自领域的决策者

如果项目变大

不是加人

而是拆项目

把一个大项目拆成多个小项目

每个小项目配一个5人团队

**不要用加人来解决问题

用拆分来解决问题**

## 结语

成本控制是Harness Coding中

最容易被忽视

但最影响可持续性的环节

很多团队

技术做得很好

但最后死在了成本上

因为Token费用、工具费用、服务器费用

加起来可能比传统团队还贵

所以

**Harness Coding不是"用AI替代人"

而是"用AI放大人"**

5个人做50个人的事

而不是5个人花50个人的钱

记住这个原则

你的Harness Coding之路才能走得更远
