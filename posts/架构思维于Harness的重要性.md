## 1. 我已经2年没有写过代码了


这个标题不是夸张

是事实

从2024年中期开始

我就再也没有亲手写过一行业务代码了

所有代码都是由Agent在Harness架构下生成的

我做的事情是

设计架构、写Spec、审核Agent的产出、做关键决策

这个转变一开始让我很不适应

因为写代码是我做了十年的事情

突然不写了

会有一种"我是不是在偷懒"的错觉

但后来我发现

不写代码之后

我有更多的时间去思考那些

"写代码时没时间思考的问题"

比如

这个系统的边界在哪里

这个架构能不能支撑未来半年的增长

这个技术选型会不会在一年后变成负债

这些问题在以前

总是被"今天要写完这个接口"的紧迫感淹没

而现在

它们终于浮到了水面之上

所以这一章

不是教你如何用AI写后端代码

而是教你如何在"不写代码"的情况下

依然能产出高质量的后端系统

甚至产出比你自己写更好的系统

## 2. AI时代下要转变的思维定势

![传统开发 vs Harness开发](https://res.cloudinary.com/isieghiq/image/upload/v1787990183/harnesscraft/3dc033d2339579a17d419f5290b6985c54c8e0a7.png)


从"写代码"到"指挥AI写代码"

最大的挑战不是工具

而是思维

以下是我认为最需要转变的几个思维定势

### 2.1 从"怎么实现"到"实现什么"

传统开发者的思维路径

需求 → 怎么实现 → 写代码 → 调试 → 完成

Harness Coding的思维路径

需求 → 实现什么 → 写Spec → Agent执行 → 验收

区别在于

传统模式下你花最多时间在"怎么实现"上

Harness模式下你花最多时间在"实现什么"上

"怎么实现"是Agent的事

"实现什么"是你的事

如果你还在花大量时间思考"这个接口用什么设计模式"

"这个查询怎么优化SQL"

那你还没有完成思维转变

你应该花时间思考的是

"这个接口的输入输出是什么"

"这个查询的预期性能是多少"

"这个功能的边界条件有哪些"

至于怎么实现

交给Agent

### 2.2 从"写好代码"到"写好Spec"

在传统开发中

代码质量是核心竞争力

在Harness Coding中

Spec质量才是核心竞争力

一份好的Spec应该包含

- 接口定义：路径、方法、参数、返回值
- 数据模型：字段名、类型、约束、索引
- 业务规则：校验逻辑、状态转换、权限控制
- 错误处理：异常场景、错误码、错误消息
- 性能要求：响应时间、并发量、数据量级
- 测试用例：正常流程、边界条件、异常流程

你会发现

写好Spec需要的不是编码能力

而是系统思考能力

你需要把一个模糊的需求

拆解成无歧义的、可执行的、可验证的描述

这比写代码难

但也比写代码有价值

因为一份好的Spec

不仅能让Agent生成正确的代码

还能在半年后帮你快速理解"当时为什么这么设计"

### 2.3 从"调试代码"到"验证Spec"

传统模式下

代码出了问题

你打开调试器，打断点，看变量

一步步追踪bug的根源

Harness模式下

代码出了问题

你首先应该问的不是"代码哪里错了"

而是"Spec哪里不够清晰"

因为大多数情况下

Agent生成的代码是符合Spec的

只是Spec本身遗漏了某些边界条件

或者Spec中的描述有歧义

导致Agent的理解和你不一致

所以debug的第一步

是回到Spec

检查Spec是否覆盖了这个场景

如果没有

补充Spec

然后让Agent重新生成

而不是直接改代码

**改代码是治标，改Spec是治本**

### 2.4 从"代码审查"到"架构审查"

传统模式下

Code Review是保证代码质量的重要手段

Harness模式下

Agent生成的代码

你逐行Review的意义不大

因为它的代码风格、命名规范、甚至设计模式

都是标准化的

你应该Review的是

- 架构是否符合预期
- 接口设计是否合理
- 数据模型是否正确
- 是否引入了不必要的依赖
- 是否有安全风险

这些是"架构审查"

而不是"代码审查"

## 3. 学这些有用不过时的知识

在AI时代

很多具体的编码技能会贬值

因为AI能做得更好更快

但有一些知识

无论AI多强大

都不会过时

因为它们是"判断力"的基础

而不是"执行力"的基础

### 3.1 系统设计

系统设计是关于

如何把一个复杂的需求拆解成多个简单的组件

以及这些组件之间如何交互

这包括

- 服务拆分：什么时候该拆，什么时候不该拆
- 数据分区：按什么维度分，分多少
- 缓存策略：缓存什么，缓存多久，什么时候失效
- 消息队列：用在哪里，怎么保证幂等
- 一致性 vs 可用性：在什么场景下选什么

这些知识不会过时

因为它们是"权衡"的艺术

而权衡需要人来做

AI可以帮你实现一个消息队列

但"这个场景要不要用消息队列"

需要你来判断

### 3.2 数据建模

数据建模是关于

如何把现实世界的业务概念

映射成数据库中的表和关系

这包括

- 范式与反范式：什么时候该规范化，什么时候该冗余
- 索引设计：哪些字段需要索引，什么类型的索引
- 数据生命周期：数据什么时候创建，什么时候归档，什么时候删除
- 数据一致性：强一致还是最终一致，怎么保证

AI可以帮你写SQL和建表语句

但"这个业务概念应该建模成一张表还是两张表"

需要你来决定

而数据建模的好坏

直接决定了系统未来半年的可维护性

### 3.3 安全意识

安全意识是关于

知道哪些地方可能出问题

以及在什么场景下需要特别注意

这包括

- 认证与授权：谁能做什么，怎么验证
- 注入攻击：SQL注入、XSS、CSRF
- 敏感数据：怎么存储、怎么传输、怎么脱敏
- 接口安全：限流、防重放、签名验证

AI可以帮你实现安全措施

但"这个接口需要不需要限流"

"这个数据字段是不是敏感信息"

需要你来识别

而且AI有时候会"好心办坏事"

比如把敏感信息写进日志

或者在前端代码中暴露内部API路径

这些都需要你的安全意识来把关

### 3.4 领域知识

领域知识是关于

你所在行业的业务逻辑和规则

如果你做金融

你需要理解风控、清算、对账

如果你做电商

你需要理解库存、促销、履约

如果你做SaaS

你需要理解多租户、权限、计费

这些知识

AI可能知道一些通用的部分

但你的业务特有的规则和逻辑

AI是不知道的

而这些特有的部分

往往是最关键的部分

所以深耕你的领域知识

是AI时代最安全的投资

**因为AI可以替代编码，但无法替代你对业务的理解**

## 4. AI时代下的后端架构设计

![后端架构五原则](https://res.cloudinary.com/isieghiq/image/upload/v1787990200/harnesscraft/99c6c278a7a6b4ac0b7f63587c9fe85e633507ba.png)


聊完思维和知识

来聊一个非常实操的话题

AI时代下的后端架构设计

在Harness Coding模式下

后端架构设计有一些新的原则

### 4.1 契约先行

在传统开发中

前后端可以并行开发

但通常需要先约定接口

在Harness Coding中

这个"约定接口"的步骤变得更加重要

因为前端Agent和后端Agent

是两个完全独立的执行单元

它们之间唯一的桥梁

就是接口契约

所以我们的做法是

在Spec阶段就定义完整的API契约

包括

- 路径和方法
- 请求参数（类型、必填、校验规则）
- 响应格式（成功和失败）
- 错误码定义
- 认证方式

这份契约一旦确定

前端Agent基于契约生成Mock和调用代码

后端Agent基于契约生成接口实现

两者并行推进

互不依赖

**契约是Harness Coding中前后端协作的唯一真理来源**

### 4.2 模块化拆分

在Harness Coding中

后端系统的模块化拆分

不仅是为了代码的可维护性

更是为了让多个Agent能并行工作

如果所有代码都在一个巨大的单体中

Agent每次修改都可能影响其他部分

你需要花大量时间处理冲突

但如果系统被合理地拆分成多个模块

每个模块有清晰的边界和接口

你就可以让不同的Agent

分别负责不同的模块

实现真正的并行开发

拆分的原则

- 按业务领域拆（用户、订单、支付等）
- 按技术层次拆（API、Service、Repository）
- 按变更频率拆（高频变更的与低频变更的分离）
- 按团队拆（不同团队负责的模块分离）

### 4.3 可测试性优先

在Harness Coding中

可测试性比以往任何时候都重要

因为Agent生成的代码

你需要通过自动化测试来验证

而不是通过逐行Review

所以架构设计时

要确保每个模块都是可测试的

这包括

- 依赖注入：方便Mock外部依赖
- 接口抽象：方便替换实现
- 纯函数化：业务逻辑尽量写成无副作用的纯函数
- 测试数据库：与开发数据库隔离

我们团队的做法是

Spec阶段就定义测试用例

Agent实现代码的同时

也要实现对应的测试代码

测试通过才算任务完成

### 4.4 可观测性内建

在Harness Coding中

代码是Agent生成的

当线上出问题时

你不能像传统开发那样

"我记得这段代码的逻辑"

因为你没写过

所以你需要依赖可观测性来理解系统行为

可观测性包括三个支柱

| 支柱 | 作用 | 实现方式 |
|------|------|----------|
| 日志 | 记录发生了什么 | 结构化日志 + 统一日志格式 |
| 指标 | 量化系统状态 | QPS、延迟、错误率、资源使用 |
| 链路追踪 | 还原请求路径 | TraceID贯穿全链路 |

在架构设计时

这三个支柱应该被内建到系统中

而不是事后添加

我们在Spec中会明确要求

"每个接口必须记录入参和出参日志"

"每个外部调用必须记录耗时和结果"

"每个请求必须携带TraceID"

这样当问题发生时

你可以通过日志、指标和链路追踪

快速定位根因

而不需要去读Agent生成的代码

### 4.5 渐进式复杂度

最后一个原则

是渐进式复杂度

在Harness Coding中

由于AI可以快速生成代码

很容易一开始就过度设计

微服务、消息队列、缓存、分库分表

一上来全用上

但这些复杂度是有代价的

部署更复杂

调试更困难

运维成本更高

所以我们的原则是

**从最简单的架构开始

只在有明确需要时才增加复杂度**

单体能搞定的

不要上微服务

数据库能搞定的

不要上消息队列

同步能搞定的

不要上异步

当且仅当你有明确的指标证明

当前架构已经成为瓶颈时

才引入更高的复杂度

而"我觉得未来可能需要"

不是一个明确的指标

## 结语

后端开发是Harness Coding中

受益最大的领域之一

因为后端开发的很多工作

是确定性的、可验证的、可自动化的

接口定义、数据模型、业务逻辑、测试用例

这些都可以被Agent很好地完成

但后端开发也是Harness Coding中

最容易"失控"的领域

因为如果没有好的Spec和架构约束

Agent生成的代码

可能比你手写的更混乱

所以

**后端的Harness化

核心不在于AI能写多少代码

而在于你能否提供足够清晰的Spec

和足够合理的架构约束**

当你能做到这一点时

你就可以像我一样

2年不写一行代码

却依然产出高质量的后端系统
