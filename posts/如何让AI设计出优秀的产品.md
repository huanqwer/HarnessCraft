## 2. 什么样的产品能称之为优秀

聊完经历

我们来聊一个更本质的问题

什么样的产品能称之为优秀

这个问题每个人可能有不同的答案

但在我看来

优秀的产品至少需要满足以下三个条件，同时对应产品经理的三大能力

![优秀产品三要素与产品经理三能力对应关系](https://res.cloudinary.com/isieghiq/image/upload/v1787791271/harnesscraft/261314ce6945a94aa09bd368fcf2d4036c13dd4f.png)

### 2.1 解决了真实存在的问题

这是最基本的要求

但也是最容易忽视的要求

很多开发者（包括我自己）在做产品的时候

经常会陷入一个误区

就是"我觉得用户需要这个"

而不是"用户真的需要这个"

这两者看起来差不多

但实际上天差地别

"我觉得"是从开发者的视角出发

"用户真的需要"是从用户的视角出发

一个优秀的产品的起点

永远是用户的真实痛点

而不是开发者的技术热情


**一个优秀的产品经理一定是某个行业或者领域深度的用户**


举个例子

你做了一个非常漂亮的Markdown编辑器

支持几十种语法高亮

支持实时预览

支持自定义主题

但如果你问用户"你用Markdown编辑器最痛苦的是什么"

答案可能是"我不知道Markdown怎么写"

而不是"我的编辑器不够漂亮"

所以你在解决一个用户没有的问题

而真正的问题你却忽略了

人很容易被自己的信息茧房困住

你以为很简单的事情是因为你已经会了

不是因为这件事情简单

就像我现在写博客一般很少写那么高深的术语和概念

而是尽量用大白话去讲，喜欢举例

因为我写的太难就没人看了


**优秀的产品经理第一步是摘下自己的大脑和成见，从用户的角度去想问题**


### 2.2 用最低的门槛解决问题

优秀的产品的第二个特征

是它解决问题的门槛足够低

这里的门槛包括

- 学习门槛：用户需要多久才能上手
- 使用门槛：用户每次使用需要多少步骤
- 认知门槛：用户需要多少前置知识

很多技术出身的产品经理

容易在这里犯错

因为我们天然倾向于"给用户更多的选择和配置"

但优秀的产品的哲学恰恰相反

**少即是多**


DeepSeek Harness出来的时候

我就在同事面前诟病它的设计

不是因为它不够酷

而是因为它就是一个很标准的「程序员设计的产品」

Cordis设计思想「万物皆插件」

听起来很酷

结果装一个DSH客户端，什么都没做

打开插件中心150+个插件？？？

那么我还是回去配置我Codex的MCPs、Skills、Rules吧

至少他们还给你分了个类

后来Pi官方也下场开始怼DSH了

这个就不详聊了

感兴趣的可以自行检索

当然DSH官方也承认现在是很初期的阶段

未来有可能（我认为极有可能）有破坏性的更新


再说一个例子：

微信刚出来的时候

很多人觉得它功能太少

连发个朋友圈都只能发图片不能发纯文字

但正是这种"克制"

让微信的门槛低到连我爸妈都会用

至于现在的微信嘛

交给你们去评论，我不评论


在Harness Coding的语境下

这一点尤为重要

因为AI可以帮助我们快速生成功能

但这不意味着我们应该把所有能想到的功能都塞进去

**克制是产品经理的一种能力，而AI不会帮你克制**


### 2.3 在解决问题的过程中带来愉悦

第三个特征可能有点主观

但我觉得很重要

优秀的产品的使用过程

本身应该是愉悦的

或者至少不是痛苦的

这里的愉悦不是指花哨的动画或者炫酷的界面

而是指交互的流畅感、反馈的即时性、以及整体的一致性


用户在使用产品的过程中

不应该感到"困惑"或者"烦躁"

每一次点击都应该有明确的预期

每一次操作都应该有及时的反馈

这一点在AI时代尤为重要

因为当AI参与到产品交互中时

如果AI的回复不可预测

反而会增加用户的焦虑

所以优秀的AI产品的设计原则之一

**是让AI的行为可预期，而不是让AI的行为更"智能"**


举个例子：

我参与设计的产品中形态最多的可能就是微信小程序了

我通常打开一个小程序后

我都会去看右上角小程序原生的几个按钮


![小程序原生按钮](https://res.cloudinary.com/isieghiq/image/upload/v1787791201/harnesscraft/a4677006b4e16dfa847ffcef418618cdd93d847a.png)

通过这几个按钮周围的设计

我就能快速判断这个小程序的产品经理的level

举一个场景，比如我们要把搜索和扫码的两个icon固定到页面的一个位置

**水货产品：**

左右下角悬浮按钮

糟糕的配色

按钮挡页面文字和其他元素

非用户高频使用的按钮

但是却引入了误触风险


**一般产品：**

自己设计一个header

把搜索和扫码icon放上去

用户使用的时候需要在页面上寻找


**高级产品：**

参考微信的布局

重新设计并计算自定义header位置

让用户无需适应

仅需遵循习惯和本能就能快速找到搜索按钮位置

利用人们经常使用微信形成的肌肉记忆

让用户无需任何guide就能快速上手


**符合用户习惯直觉的产品才是好产品**

当然不要和我说Apple可以定义用户习惯的公司和产品案例

我想大部分人做不到，我也做不到

## 3. AI时代下的产品经理

聊完什么是优秀的产品

我们来聊一个角色

产品经理

在AI时代下

产品经理这个角色正在发生哪些深刻的变化

### 3.1 传统产品经理 vs AI时代产品经理

传统产品经理的核心能力

是"翻译"

把用户的需求翻译成开发能理解的需求文档

把开发的实现翻译成用户能理解的功能说明

把老板的战略翻译成团队能执行的迭代计划

但在AI时代

这个"翻译"的工作

AI自己就能做

而且可能做得比人更快更全

所以AI时代的产品经理

核心能力不再是"翻译"

而是"判断"

判断什么值得做

判断什么不值得做

判断什么是用户的真实需求

什么是用户的伪需求

判断什么时候该坚持

什么时候该放弃

**翻译可以外包给AI，但判断不能**

放到任何别的领域也是一样

所以AI时代我一直推荐大家去学那些「古董知识」

产品思维、技术判断力、心理学、管理学等等


### 3.2 产品经理的Harness化

在Harness Coding的架构下

产品经理的工作可以被拆解为以下几个Agent

| Agent | 职责 | 输入 | 输出 |
|-------|------|------|------|
| BA Agent | 需求分析、用户调研 | 用户原始描述、市场数据 | 需求文档、用户画像 |
| Design Agent | 原型设计、交互设计 | 需求文档 | 原型图、交互流程图 |
| PM Agent | 优先级排序、迭代规划 | 需求池、资源约束 | 迭代计划、优先级矩阵 |
| Validation Agent | 市场验证、数据分析 | 产品原型、用户反馈 | 验证报告、改进建议 |

这四个Agent互相协同

形成一条从"需求"到"验证"的完整流水线

![产品经理Harness化Agent协作流水线](https://res.cloudinary.com/isieghiq/image/upload/v1787791282/harnesscraft/c942057f3743c0c26cd2118f47b59fdeaf3d1bd6.png)

而作为人类产品经理

你的角色从"执行者"变成了"指挥官"

你负责设定方向、审核结果、做出关键判断

具体的执行交给Agent


### 3.3 提示词工程是产品经理的新核心技能

在AI时代

产品经理最重要的新技能

不是写代码

不是画原型

而是提示词工程

因为提示词工程本质上就是"把模糊的需求结构化"的能力

这恰恰是产品经理最核心的工作


我在面试AI产品经理的时候

最爱问的一个问题

「你觉得AI时代下的产品经理的工作流程会发生怎样的转变」

如果还是回答传统流程那一套

类似什么需求分析，用Figma画原型

我就会大失所望

但是如果知道利用现在最强的生图模型去画原型

那么就会让我眼前一亮

如果知道生图结束后

怎么将图转换成Demo或者MVP

那么就已经是中上游水准的产品经理了

我发现一个很有意思但是很普遍的现象

「AI产品经理设计AI应用的时候居然不使用AI」


我们书接上文：

一个好的提示词

需要包含

- 明确的目标：你要AI做什么
- 清晰的约束：有什么限制条件
- 具体的上下文：背景信息是什么
- 可衡量的验收标准：怎样算做好了

你会发现

这跟写一份好的需求文档

本质上是一回事

所以产品经理在AI时代

不是被淘汰了

而是被升级了

**从"写文档的人"升级为"写提示词的人"**

## 4. 快速出产品原型

聊完产品经理的角色变化

我们来聊一个非常实操的话题

如何用Harness Coding快速出产品原型

在传统的开发模式中

从想法到原型

可能需要几周甚至几个月

但在Harness Coding模式下

这个时间可以被压缩到几天甚至几小时


### 4.1 原型的三个层次

在Harness Coding中

我通常把原型分为三个层次

| 层次 | 名称 | 目的 | 工具 | 耗时 |
|------|------|------|------|------|
| L1 | 概念原型 | 验证想法是否成立 | 对话Agent + 文档 | 数小时 |
| L2 | 交互原型 | 验证流程是否顺畅 | IDE Agent + UI框架 | 数天 |
| L3 | 功能原型 | 验证功能是否可用 | CLI Agent + 全栈框架 | 数周 |

L1原型可能只是一份结构化的需求文档加几张流程图

但它能帮你快速判断"这个想法值不值得继续投入"

L2原型是一个可点击的界面

用户可以走完核心流程

但后台可能是Mock数据

L3原型是一个可运行的最小可用产品

有真实的后端

有真实的数据库

但功能只覆盖核心路径

![原型三个层次](https://res.cloudinary.com/isieghiq/image/upload/v1787791270/harnesscraft/489275bec2df075d7704ca64878808ed052f57d5.png)


### 4.2 用AI生成概念原型

概念原型的生成流程

1. 用对话Agent描述你的产品想法
2. 让Agent帮你生成需求文档和用户画像
3. 让Agent帮你识别核心用户旅程
4. 让Agent帮你生成竞品分析
5. 审核并修正Agent的输出

这个过程的关键

不是Agent的输出有多完美

而是你在审核过程中

会不断发现自己想法中的盲点

**Agent的价值不是替你思考，而是帮你思考得更全面**


### 4.3 用AI生成交互原型

交互原型的生成流程

1. 基于概念原型的需求文档
2. 用IDE Agent生成前端页面
3. 指定UI框架（如Tailwind、Ant Design等）
4. 让Agent生成Mock数据和页面跳转逻辑
5. 走查核心用户流程

这里有一个技巧

就是先让Agent生成"线框图"级别的页面

确认布局和流程没问题后

再让Agent做视觉优化

不要一上来就追求像素级完美

因为布局和流程的修改成本

远低于视觉的修改成本


这里也分享我自己的一个小技巧：

**如果你要打造一条产品线或者系列而非单个产品**

**建议先做一套自己的组件库和风格原型**

**让AI生成任何页面都去组件库里拿**

**比直接让AI自由发挥稳定得多**

细节我在后续关于前端的章节中再聊


### 4.4 用AI生成功能原型

功能原型的生成流程

1. 基于交互原型确认的核心流程
2. 用CLI Agent搭建后端服务
3. 定义数据模型和API接口
4. 让Agent生成数据库迁移和种子数据
5. 前后端联调

在这个阶段

Harness的优势开始显现

因为你可以让不同的Agent分别负责前端和后端

通过Spec契约约束它们的接口

实现真正的并行开发

这里也不再赘述

我会在后续关于开发和最佳实践的章节说明


所以你会发现，AI时代下优秀的产品经理

其实就是一个基于Harness和各种方法论的

「OPC一人公司」（One Person Company）

## 5. 如何验证市场

最后一步

也是最重要的一步

验证市场

很多开发者（包括我自己）

最容易犯的错误就是

花了几个月做产品

结果发现根本没人要


所以验证市场这件事

应该越早越好

### 5.1 验证的三个阶段

| 阶段 | 名称 | 验证目标 | 方式 | 成本 |
|------|------|----------|------|------|
| V1 | 概念验证 | 用户是否对想法感兴趣 | 落地页 + 邮件订阅 | 数小时 |
| V2 | 原型验证 | 用户是否愿意使用 | 原型测试 + 用户访谈 | 数天 |
| V3 | 付费验证 | 用户是否愿意付费 | MVP + 付费墙 | 数周 |

很多开发者跳过了V1和V2

直接做V3

这就是"花了几个月做产品结果没人要"的根本原因

![市场验证三阶段](https://res.cloudinary.com/isieghiq/image/upload/v1787791279/harnesscraft/c79d2954d9768b08af79e039055afdf45458b20b.png)


### 5.2 用AI加速验证

在Harness Coding模式下

验证的每个阶段都可以用AI加速

**V1概念验证**：

用AI生成落地页的文案和设计

用AI生成SEO友好的博客文章引流

用AI分析订阅用户的来源和行为

**V2原型验证**：

用AI生成用户访谈的问题清单

用AI分析用户的使用路径和停留时长

用AI总结用户反馈并识别共性问题

**V3付费验证**：

用AI生成定价策略和付费方案

用AI分析转化漏斗的每个环节

用AI生成A/B测试方案并分析结果


### 5.3 验证的核心原则

无论用什么工具

市场验证的核心原则始终是

**用最小的成本获取最真实的信号**

"最小成本"意味着不要在验证阶段过度投入开发

"最真实信号"意味着要观察用户的实际行为

而不是用户说的话

用户说"我会用"和用户真的用了

是两回事

用户说"我会付费"和用户真的掏钱了

也是两回事

所以验证的重点

永远是行为数据

而不是问卷结果

在Harness Coding模式下

你可以用Agent帮你收集和分析行为数据

但"判断这个信号是否值得继续投入"

仍然需要你自己来做

**AI可以帮你看见数据，但无法替你做出决定**

## 结语

产品设计是Harness Coding中最容易被忽视

但最重要的环节

因为代码可以由AI生成

但"做什么"和"为什么做"

始终需要人来判断

在AI时代

产品经理不是被淘汰了

而是被升级了

从"写文档的人"升级为"写提示词的人"

从"翻译需求"升级为"判断方向"

从"执行流程"升级为"指挥Agent"

而Harness Coding给我们的最大启示是

**当你能快速出原型、快速验证市场时

最大的风险不再是做不出来

而是做出来没人要**

所以把更多的时间花在"验证值不值得做"上

少花时间在"怎么做得更完美"上
